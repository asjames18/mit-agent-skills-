# Evaluation Dimensions

Evaluate the named product against the user's problem. Skip a dimension only when the chosen tier explicitly allows it; otherwise mark it **Unknown**.

## Capabilities

What the product actually does, in the versions and editions supported by current official sources. Separate core features from add-ons, betas, and roadmaps. A roadmap item is not a capability.

## Fit

Whether those capabilities address the stated problem and workflow, including inputs, outputs, operators, and constraints the user named. A generally strong product can still be a poor fit.

## Implementation effort

Publicly visible integration, migration, skill, and operating cost: APIs, SDKs, hosting model, required adjacent tools, and what a first working path would involve. Do not invent internal headcount or calendar estimates.

## Security and privacy

Authentication, authorization, data handling, retention, training-data use, subprocessors, and documented compliance artifacts. Treat badges, "enterprise-ready" language, and unchecked whitepapers as **Vendor claim** until an official control description or independent assessment supports them.

## Pricing and limits

Public list pricing, free-tier quotas, rate limits, seat or usage metrics, and overage rules from an official source checked during this task. If public pricing is absent, record **Unknown**. Never substitute private, promotional, or remembered prices.

## Limitations

Documented gaps, unsupported regions or platforms, lock-in, maturity, operational constraints, and cases the vendor says the product is not for. Absence of a limitation in marketing copy is not evidence that the limitation does not exist.

## Alternatives

Comparable public options, including the user's current tool when named. Use the same dimensions for each option. Do not introduce an alternative as a straw man or as the review's true subject unless the user asked for a comparison.

## Approval and access implications

Generic implications of adopting or testing the product: new vendors, data leaving a current boundary, required review types such as security, legal, or procurement, and access patterns such as SSO or API keys. Keep this portable. Do not assume a specific organization's process, tools, or approvers.
